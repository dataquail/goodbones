description: A campaign's record of every place the pattern still occurs, and of every time the count was allowed to go up.

Each [campaign](/goodbones/architecture-rules/manifest/campaigns/) has a ledger: one JSON file
under the manifest's `ledger` directory (default `.architecture-campaigns/`), named
`<id>.json`. It is the [baseline](/goodbones/architecture-rules/enforcement/baseline/)'s
cousin and not the baseline — same fingerprint, different file, different semantics. A
baseline records violations a repository is carrying; a ledger records debt a campaign is
paying down, and the file is where the burn-down lives.

```json
{
  "version": 1,
  "id": "react-class-components",
  "created": "2026-09-15T14:02:00.000Z",
  "initial": 412,
  "fixed": 26,
  "lastProgress": "2026-09-14T09:11:00.000Z",
  "regressions": [
    {
      "at": "2026-09-10T16:40:00.000Z",
      "by": "someone@example.com",
      "delta": 2,
      "reason": "Vendor SDK wrapper only ships a class API until v4",
      "entries": ["apps/web/src/vendor/Widget.tsx#Widget", "apps/web/src/vendor/Panel.tsx#Panel"]
    }
  ],
  "entries": [
    "apps/web/src/checkout/CartPanel.tsx#CartPanel",
    "apps/web/src/checkout/Totals.tsx#Totals"
  ]
}
```

Entries are `file` or `file#subject`, deduplicated and sorted, one per line — so a pull
request that fixes three of them is a three-line deletion a reviewer can read. One file per
campaign, so two pull requests migrating different components never conflict, and finishing
a campaign is deleting its file.

## The arithmetic

The count is not stored; it is `entries.length`, and `check` verifies that

```
entries.length === initial + Σ regressions.delta − fixed
```

An entry added by hand, with no regression record, fails the build — with no git history in
the loop. That is what keeps the file honest: every number in it is derivable from the
others, and the only way the count rises is through a record of why.

## The three commands

```bash
architecture campaigns                                    # the status table
architecture campaigns init react-class-components        # the first ledger, from what fires today
architecture campaigns prune [react-class-components]     # drop what no longer fires
architecture campaigns allow react-class-components --reason "vendor SDK ships a class API until v4"
```

**`init`** writes a campaign's first ledger: every hit is an entry, and the count is the
`initial`. It refuses to overwrite one; `prune` and `allow` are how a ledger changes. Until
a campaign with hits has a ledger, `check` fails and says which command to run.

**`prune`** only removes. A ledger entry the code no longer produces is stale, and `check`
fails on it exactly as it fails on a stale baseline entry:

```
campaign react-class-components: 3 ledger entries no longer fire. The code was fixed; prune them:
  apps/web/src/checkout/CartPanel.tsx#CartPanel
  …

  architecture campaigns prune react-class-components
```

Pruning bumps `fixed` by as many and stamps `lastProgress` — so progress lands as a visible
diff, and the stall clock reads it. A `match` entry whose hash moved under a still-present
declaration is rewritten in place and counts as neither fixed nor new.

**`allow`** is the only command that adds entries, and it always appends a regression
record: the entries, a reason, a timestamp, and an author — `--by`, else git's
`user.email`, else `GIT_AUTHOR_EMAIL`, and refused without one. A hit the ledger does not
carry is unrecorded growth, and `check` fails on it with the campaign's `how`:

```
campaign react-class-components: 1 new hit the ledger does not carry. Fix it, or record why the count may rise:
  apps/web/src/vendor/Widget.tsx  (Widget)
      [campaign/react-class-components] Convert to a function component. …

  architecture campaigns allow react-class-components --reason "<why>"
```

`--entries a,b` allows a subset and leaves the rest failing, for a pull request that
legitimately adds one hit while another is an accident.

## What a reviewer looks for

The ledger is designed to be read in a diff. A line deleted from `entries` and `fixed`
going up by one is progress. A line added to `entries` must come with a new object under
`regressions` naming it, with a reason the reviewer agrees with; a line added without one
does not pass `check`, so it will not be in a green pull request. `lastProgress` moving is
someone having paid something down; `regressions` growing is the count going up, on
purpose, with a name on it.

Because the file is per campaign and the records name their author, `CODEOWNERS` on the
ledger directory puts the campaign's owner on every change to its count:

```
.architecture-campaigns/react-class-components.json  @dataquail/web-platform
```

## Stalls and completion

Every campaign states `staleAfter`. A campaign with entries left whose `lastProgress` is
older than that is **stalled** — a notice in `check`, and the first thing
[`conformance`](/goodbones/architecture-rules/enforcement/conformance/) prints in its
campaigns section, since a migration nobody is working on is the failure the whole apparatus
exists to make visible.

A campaign at zero is **complete**. What happens next is its `onComplete`: `keep` leaves
it in the manifest as a guard against recurrence — a new hit is unrecorded growth like any
other — and `remove` makes `check` fail until the campaign and its ledger are deleted, so
a finished migration does not linger as a rule about nothing.

`ARCHITECTURE_NOW` (an ISO date, or epoch milliseconds) pins the clock every timestamp and
stall is judged by, for a CI that replays a day or a test that needs a stall to have
happened.
