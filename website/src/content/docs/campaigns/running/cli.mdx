---
title: Commands
description: Command reference for the campaign verbs of the architecture CLI.
---

Campaign commands are subcommands of the `architecture` bin (see
[the CLI](/goodbones/architecture-rules/enforcement/cli/)). `check` also verifies every campaign
against its ledgers, and `explain <file>` shows a file's sector, phase and each objective's result.

| Command                      | What it does                                                                |
| ---------------------------- | --------------------------------------------------------------------------- |
| `campaigns`                  | status table: progress, owner, stalls, phases, per-objective burn-down      |
| `campaigns status --changed` | [the nudge](/goodbones/campaigns/running/nudge/) for the current diff       |
| `campaigns status --sector`  | where one sector stands, and every holdout that keeps it there              |
| `campaigns attest`           | record that a sector passed an attested phase                               |
| `campaigns note`             | leave a remark on a sector for the next person                              |
| `campaigns history`          | the ledgers' git history, one row per commit                                |
| `objectives clear`           | reconcile the [ledgers](/goodbones/campaigns/running/ledger/) with the code |
| `objectives concede`         | record why a count may rise                                                 |

Every command takes optional roots to walk after its arguments. A root that is not a path in the
repository is refused rather than walked; when it names a sector, the refusal points at
`--sector`. `campaigns clear` and
`campaigns concede` are aliases for the `objectives` verbs. `campaigns init`, `prune` and `allow`
were removed and are refused with a pointer to their replacement.

Where a command records an author, it uses `--by <email>`, else git's `user.email`, else
`GIT_AUTHOR_EMAIL`. `attest`, `note` and `concede` fail without one.

## `campaigns`

```
$ architecture campaigns

1 campaign under packages

  lowering-reports-not-throws   21%     15 left  @dataquail
    throws-in-lowering   21%     15 left  4 cleared  2 conceded
```

A campaign with phases prints where its sectors stand, and its headline is read off that:

```
  strangle-hapi   30%     23 left
    phases: fenced 3 → rebuilt 1 → mirrored 0 → served 1 → routes-moved 0 → settled (open) 0
    no-role-checks     40%      6 left  4 cleared  0 conceded
    routes-still-local 25%      6 left  2 cleared  0 conceded
    no-hapi-routes       —      0 left  no sector has entered its window
```

- **The headline** is how far along the ladder the sectors are, averaged. A sector's position is
  the phases behind it plus the share of its current phase that is paid, over the number of
  defined phases. A sector at the open phase has taken every step. So the number rises as
  sectors advance, and it does not fall when a sector enters a phase and that phase's holdouts
  are counted for the first time.
- **An objective's row** keeps its own ratio: cleared over everything the ledger was ever asked
  to carry. An objective no sector has entered prints `—`. Nothing has been asked of anyone yet,
  which is neither 0% nor 100%.
- A campaign with no phases has no ladder, and its headline is the same ratio as its objectives'.

`campaigns --json`, and `campaigns status --json` without `--changed`, print the campaigns as the
conformance snapshot carries them, a row per sector included. `architecture conformance --json` carries the same numbers: `progress` and `steps` on a campaign,
`position` on a sector, and `entered` and `progress` (`null` before any sector enters) on an
objective.

## `campaigns status --changed`

```bash
architecture campaigns status --changed [--base <ref>] [--json] [--hotfix "<reason>"] [--by <email>]
```

| Flag                  | Meaning                                                                      |
| --------------------- | ---------------------------------------------------------------------------- |
| `--changed`           | required                                                                     |
| `--base <ref>`        | compare against this commit instead of the ledger and `HEAD`                 |
| `--json`              | print the JSON document                                                      |
| `--hotfix "<reason>"` | concede growth `ratchet` or `paydown` would refuse; verdict becomes `hotfix` |
| `--by <email>`        | author of the hotfix concession                                              |

Exits non-zero when any sector's verdict is `back` or `no-paydown`.

## `campaigns attest`

```bash
architecture campaigns attest <sector> <phase> --reason "<why>" [--evidence <url>] [--by <email>] [--campaign <id>]
```

`--reason` is required. Accepted only while the sector is at that phase. Run `objectives clear`
afterwards to move the sector on. See
[Attested phases](/goodbones/campaigns/manifest/attested/) for the shape.

## `campaigns status --sector`

```bash
architecture campaigns status --sector <sector> [--campaign <id>] [--json]
```

Where one sector stands and what holds it there, without a file to `explain` or a ledger to read:
the phase and its intent, the furthest phase reached, the attestations, what counts toward the
next phase, every holdout in window by objective (with its location and the objective's `how`),
each scalar in window with what it is held to, and the sector's notes.

```
strangle-hapi · billing — phase served (5 of 9), reached served since 2026-10-02
  intent: The Nest module answers: hapi's routes forward to it operation by operation.
  attested backfilled: 2026-10-02 by dev@example.com — backfill ran on staging and prod
  toward the next phase: routes-still-local 3 · legacy-writes 4
  routes-still-local — 3 holdouts in window: Forward the route to the Nest server.
    packages/legacy-api/src/application/billing/billing-routes.ts:43  billingRoutes
    …
  hapi-lines: 712 (held to 712, tolerance 20)
```

A sector of that name in several campaigns is shown once per campaign; `--campaign` picks one.
`--json` prints `{ version: 1, sectors: [...] }`.

## `campaigns note`

```bash
architecture campaigns note <sector> "<text>" [--by <email>] [--campaign <id>]
```

A note is at most 500 characters, and a sector holds at most 20. Past either, `note` refuses and
records nothing: it never cuts a note or drops an old one to make room. Split a long note, or prune
the sector's record in its own commit.

`attest` and `note` need `--campaign <id>` when the policy declares more than one campaign.

## `campaigns history`

```bash
architecture campaigns history [<campaign>] [--since <ref>] [--json]
```

Walks the git history of the ledgers and manifest from `--since <ref>`, one row per commit.
Without `<campaign>`, covers every campaign.

## `objectives clear`

```bash
architecture objectives clear [<campaign>[/<objective>]] [--by <email>]
```

Reconciles every ledger, or just the one named: removes holdouts that stopped firing, rewrites
drifted ones, records sectors entering a window, closes sectors leaving one, re-baselines after a
phase concession, and writes each sector's `reached` and the plan. It never adds a holdout. For a
[scalar objective](/goodbones/campaigns/manifest/scalars/), it records an improved value.

## `objectives concede`

```bash
architecture objectives concede <campaign>[/<objective>] --reason "<why>" [--sector <name>] [--holdouts a,b] [--by <email>]
```

| Flag              | Meaning                                                                      |
| ----------------- | ---------------------------------------------------------------------------- |
| `--reason`        | required                                                                     |
| `--sector <name>` | only this sector                                                             |
| `--holdouts a,b`  | only these holdouts; the rest still fail. Alias `--entries`. Not for scalars |
| `--by <email>`    | author                                                                       |

Name the objective when the campaign has more than one. For a scalar objective, `concede` records
the rise as `{ from, to }`.
