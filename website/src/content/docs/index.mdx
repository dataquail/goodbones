## Architecture Rules

`@goodbones/oxlint` and `@goodbones/cli` turn architecture policy into one manifest of your repository —
import boundaries, export sites, member vocabularies and file taxonomy, all resolved to real
files and enforced by oxlint.

<CardGrid>
  <Card title="One manifest, not a rule list" icon="document">
    A tree keyed by path pattern, where everything the architecture says about a part of
    the repository is written **at that part of the repository** — its imports, its
    importers, its members, the siblings it owes, the children it admits.

    [Read the overview →](/goodbones/architecture-rules/manifest/)

  </Card>
  <Card title="Real resolution" icon="approve-check">
    Every pattern is matched against a **resolved** file path, through your `tsconfig`
    `paths` and your workspace links. A rule about `@/modules/user` is a rule about the
    file that specifier actually names.

    [How resolution works →](/goodbones/architecture-rules/enforcement/resolution/)

  </Card>
</CardGrid>

<CardGrid>
  <Card title="Tight by default" icon="setting">
    A folder admits only the children it lists; a file may import only what it or an ancestor
    allows. Laxity is opted into by name — `reset`, `unrestricted`, `layout: open` — so widening is
    a sentence someone wrote, and `grep` is the adoption backlog.
  </Card>
  <Card title="Every rule proves itself" icon="warning">
    Each compiled rule carries a probe generated from its own node path, and the plugin **refuses to
    load** if any rule fails it. A rule that has drifted into matching nothing is a load-time error,
    not something a separate script might notice later.
  </Card>
  <Card title="A ratchet, not a suppression list" icon="seti:config">
    The baseline records violations a repository carries while it adopts a rule, keyed by a
    line-independent fingerprint. Fix one and the build fails until its entry is gone, so the floor
    only ever rises.
  </Card>
  <Card title="Two ways to ask" icon="seti:typescript">
    An oxlint plugin for the editor and CI, and a CLI that evaluates the same policy with no linter
    in the loop. Both answer to the same core, so an alpha plugin API is not a single point of
    failure.
  </Card>
</CardGrid>

## Campaigns

`@goodbones/campaigns` tracks a multi-step refactor as an object in the same manifest: objectives
with ledgers that only shrink, over the sectors of code that move through it, through phases you
define as you learn them — and a nudge that tells whoever touches a sector what would move it on.

<CardGrid>
  <Card title="A refactor you can measure" icon="list-format">
    Each objective records every place its pattern still occurs, per sector. The count only goes
    down on its own; growth needs a recorded reason.

    [Read the introduction →](/goodbones/campaigns/getting-started/introduction/)

  </Card>
  <Card title="A plan written as you learn" icon="random">
    Define the phases you know and leave the rest open. As sectors reach the edge of the plan, the
    next step becomes clear and is written down.

    [How phases work →](/goodbones/campaigns/manifest/phases/)

  </Card>
</CardGrid>
